Audit baseline: main at 20cd7ba, clean working tree. Existing `src/cli/bench.ts` has four fixture scenarios, three hidden Go acceptances, live Claude/platform driving, fake Git PRs and persistence to `eval_results` (migration 011). `src/eval/summary.ts` and `Insights.tsx` summarize these results. Existing examples and tests are not verified historical completed tickets; the new golden cases will be labeled synthetic, with provenance to these examples where applicable.

Reuse: existing workflow definitions, integration executors, PostgreSQL workflow_jobs leasing/fencing/cancellation, checkpoints/questions/resume, execution ownership, workflow artifacts and attempt metrics. Reuse the registry and worktree records for fixture repositories, and P1 parsing/index/search/context in ON/OFF runs. Keep legacy eval summary/API output compatible.

Missing: immutable suite/case manifests and pinned commits; independent validators; hard gates and versioned scoring; paired repetitions/regression decisions; owner-scoped benchmark launch/detail/comparison APIs; a safe fixture-only execution path; reproducible output and cleanup. The previous CLI does not constitute a safe generic live benchmark runtime: fake PRs alone do not prevent network/API side effects, and it silently auto-answers human gates.

Implemented: migration 027 adds versioned suite/case/config/execution records and extends eval_results rather than replacing it. Each case is an existing integration workflow step, with validation artifacts on the existing workflow run. Human cases use existing WAITING_INPUT/checkpoint resume. Frozen configs and scoring/gates are persisted. Managed fixture Git repositories live under local dataDir; no business checkouts are edited. P1 flag overrides use existing AsyncLocalStorage execution scope, never process-global mutations. Bounded, networkless container validation uses an already installed local image with no pulls; unavailable isolation blocks execution. Live runs require explicit approval and remain blocked without a verified safe provider connector/cost boundary. New UI stays within Insights.

Compatibility risks: fixture registry entries must not enter ordinary project discovery; A/B flags must not leak across concurrent runs; missing cost/tokens must remain unknown; legacy evaluation rows without owners must not become private-data leaks; stale workers must not overwrite results or remove newer workspaces. Existing migration history remains unchanged and production defaults stay off.

## Execution and persistence

`src/eval/service.ts` publishes `backend-v1@3`, validates immutable pinned fixtures, freezes configurations and creates private existing workflow definitions. Each case is a `benchmark_case` integration step, claimed through the existing PostgreSQL scheduler. Case retries use the normal job policy; the synthetic transient case intentionally fails once. Publication locks the parent workflow and verifies the current attempt, live job lease and platform instance session. Replayed completed cases return their existing result. Worktrees include attempt identity, so expired workers cannot remove a newer attempt's files. Cancellation and worker restart reuse existing recovery rather than a second queue.

Dataset/config immutability is enforced by PostgreSQL triggers and hashes. Fixture commits have fixed Git identities and timestamps; source trees, harness code, validation/scoring versions, image digest and Node closure are recorded. Changing a harness file requires publishing a new suite version. `eval_results` holds scores/evidence and references existing workflow artifacts for bounded diffs, context and checks. Reporting loads results in batches. Legacy rows retain their previous visibility; new owned results require the matching owner. Administrators publish suites, but cannot inspect another user's private evaluation through these APIs.

`src/eval/runner.ts` supports unchanged baseline and declared reference-patch controls, plus `agent_fixture`, which calls the real executor with the existing deterministic Codex process fixture. Fake provider counters are discarded. The benchmark independently validates the resulting files; a successful explanation without a patch fails. The reference controls are labeled scripted, including their clarification answers. No live provider runs are launched.

## Isolation and limits

The current validator uses an existing local container image through the `docker` command (Podman here). It pins the inspected image ID and mounts only the Nix Node runtime closure, validator, TypeScript compiler and disposable fixture directories. It passes no host credentials, disables networking, drops capabilities, runs as the current unprivileged UID, and limits memory, PIDs, CPU, temporary storage, output and wall time. Podman's container-enforced `--timeout` also bounds orphan containers after a worker crash. A runtime probe verifies network and cgroup limits. Unsupported runtime, permissions, image or probe failures produce BLOCKED.

This adapter currently requires Linux, Nix and a Podman-compatible CLI with `--timeout`. It does not silently fall back to host execution. Production Docker portability and paid-provider execution need a separately verified adapter. The image contains validation tools only and is not a new persistent infrastructure service.

Defaults in local configuration: `evaluation.enabled=false`, `maxCases=20`, `maxRepetitions=3`, `maxCaseSeconds=30`, `maxTokens=20000`, `maxCostUsd=2`, `maxLiveAgents=1`, `sandboxImage=docker.io/library/postgres:17-alpine`. Per-run limits can only tighten these bounds. Fixtures record zero provider cost and unknown provider tokens. Live mode requires explicit administrator approval and still returns BLOCKED because hard spending and external-side-effect controls are not yet verified. No LLM judge runs.

## Validation and scoring

Order: verify repository/tree/configuration and allowed paths; syntax parsing and actual TypeScript compilation; public tests; private behavioral/regression checks; structural SQL/proto checks and capability restrictions; score the evidence. Private checks are mounted after implementation outside writable fixture directories. Hidden acceptance assertions are independent of the reference patches. Proto checks preserve field numbers/RPC contracts; SQL checks require parameterized keyset pagination. These are structural checks, not protoc compilation or database query-plan measurement.

`objective-v1` weights are functional correctness 40%, regression safety 20%, requirement coverage 15%, code quality 10%, reliability 10%, efficiency 5%. Values are explicit fixture assertions; code quality is a limited syntax/security/path proxy, not a maintainability judgment. Efficiency compares measured duration to its frozen budget. Hard gates override the weighted score; unavailable execution is BLOCKED. Missing tokens/cost remain unknown, and malformed observed usage is rejected. Correctness and requirement coverage currently share behavioral evidence, a documented limitation.

Comparisons require identical suite, repositories, repetitions, execution limits, validator/scoring/runtime identities. Configurable policies enforce minimum paired samples/repetitions, success tolerance, critical task/security rules, and cost/latency warnings. Missing or blocked cases cannot yield PASS. Reports retain individual repetitions, Wilson success intervals, standard deviations and sample sizes. Repeated synthetic controls are correlated and do not establish model superiority.

## Operations

Use the existing application migration startup to apply 027 to the intended database. Migration is additive and forward-only, matching the existing framework; it preserves legacy eval rows. Enable only through the local config. Publish through `POST /api/benchmark-suites/publish` as administrator, create/start through `/api/evaluation-runs`, inspect/cancel through the run routes, and compare through `/api/evaluation-comparisons`. Insights → Quality exposes these operations and existing workflow artifact/question links.

`npm run bench -- --suite=backend-v1 --repetitions=2` is a local-only reference OFF/ON driver. It uses persistent `platform_bench`, never drops it, and writes its full evidence report to `EVAL_REPORT` if supplied. Legacy graph-only benchmarks use uniquely named disposable databases and cannot launch their former unbounded live paths. Evaluation completion suppresses outbound notifications, forced learning models and memory promotion. Managed fixture repositories cannot enter normal project selection or startup indexing.

Known recovery boundary: evaluation creation calls existing workflow creation within its surrounding transaction. A crash between those transactions can leave a non-runnable PENDING workflow without an evaluation row; it cannot launch a case, but currently needs administrative cleanup. Completed attempt worktrees are removed; immutable datasets and audit artifacts are retained intentionally. See [validated results and remaining gaps](../validation/p2-finalization.md).
